# Инструкции для AI-агентов

## Правила работы с репозиторием

- Всегда создавай новую ветку от актуального `main`.
- Не трогай файлы, которые не указаны в задаче.
- После изменений создавай PR.
- Язык комментариев в коде и коммитов — русский.

### Работа с бэклогом

- Структура docs/backlog.md фиксирована: 4 секции — «До релиза», «После релиза», «Бэклог», «Архив». Секция «Бэклог» имеет фиксированные подзаголовки: Парсеры, AI, HH-сканер, Аналитика рынка, Инфра. Новые секции и подзаголовки не создаются без явного решения.
- Формат задачи: `- [ ] [Index] Краткое описание (файлы)`; одна строка, без вложенных списков и абзацев; задача однозначно отвечает на три вопроса: ЧТО изменится, ГДЕ (файлы), КОГДА ГОТОВО (критерий); если формулировку можно прочитать двумя способами — дополнить уточняющей фразой через точку с запятой, не выносить в подпункт.
- При каждом PR проверяй docs/backlog.md: выполненную задачу помечай `[x]`, очищай индекс T-XXX и переноси только формулировку в секцию «Архив»; удалять задачи запрещено.
- Новые задачи добавляй в конец соответствующей секции; для секций «До релиза» и «После релиза» присваивай следующий порядковый индекс T-XXX; порядок внутри секции не меняется без явного указания.
- Статус `[?]` — задача с неопределённым состоянием, требует ручной проверки; не трогай без явного указания.


## Правила работы с остальной документацией

- Если PR добавляет новую команду, callback-prefix, архитектурный паттерн или меняет поведение, обнови документацию в том же коммите.
- Обновляй `README.md`, если меняются команды бота или структура проекта.
- Обновляй `AGENTS.md`, если меняются правила работы агента или архитектурные паттерны.
- Обновляй `docs/context.md`, если принимается продуктовое или архитектурное решение.
- Обновляй `docs/bugs.md`, если исправляется баг: добавляй запись в конец файла по шаблону.


## Архитектурные принципы

- Список компаний, эмодзи и категории берутся из таблицы `companies` в Supabase, не хардкодить.
- При добавлении новой компании обязательно заполнить `sort_name` — русская транслитерация названия для сортировки (например, Lamoda -> Ламода). `sort_name` используется в `get_company_page` для порядка отображения.
- В user-facing слое (`callback_data`, mute/unmute-команды, карточка вакансии) использовать `slug` из таблицы `companies`, не `parser_name`. `parser_name` может повторяться у компаний одного парсера.
- Эмодзи компаний формируются через `format_company_emoji`: если заполнен `custom_emoji_id`, используется тег `tg-emoji`, иначе обычный `emoji`. Не хардкодить id в коде, брать из таблицы `companies`.
- Города нормализуются через таблицу `city_mappings` в Supabase, не хардкодить. Исключение: `CITY_OPTIONS` в онбординге — осознанное UX-решение.
- Один парсер = один файл в `parsers/`.
- Любой новый парсер обязательно регистрируется в `PARSER_REGISTRY` в `parsers/__init__.py`.
- При добавлении нового парсера обязателен INSERT в таблицу companies в Supabase (name, parser_name, emoji, is_enabled). Без записи в companies парсер не запустится — get_enabled_companies() его не вернёт.
- Запрещено использовать точные хешированные CSS-классы (паттерн ComponentName__element_hash) как основной селектор для извлечения данных. Такие классы меняются при каждом деплое сайта. Использовать семантические теги (main, article), data-атрибуты, aria-атрибуты, JSON-LD, или слабые class-fragment селекторы ([class*="content"]) только как подсказку.
- Парсеры импортируются только через `PARSER_REGISTRY`, не через `importlib`.
- Ошибка одного парсера или enrichment не должна останавливать остальные.
- Ошибки парсеров классифицируются в main.py функцией _classify_parser_error по типу исключения. Теги: [BLOCKED], [TIMEOUT], [NOT_JSON], [HTTP_xxx], [VALUE_ERROR], [ERROR]. Классификация происходит в main.py, не в парсерах.
- Telegram API вызовы идут только через `bot/telegram_api.py`, не через прямой `requests.post`.
- Telegram-сообщения используют `parse_mode="HTML"`, не Markdown.
- Пустые поля (`None`, `""`, `"Не указан"`) не показываются пользователю.
- Названия вакансий перед сохранением нормализуются через `.strip()`.
- `content_hash` определяет, нужно ли обновлять вакансию.
- `enrich()` вызывается только для новых и изменённых вакансий, до normalizer, и не должен перезаписывать уже заполненные поля.
- Контракт enrich(): метод мутирует dict in-place, вызывается до normalizer. Не перезаписывает поля, которые уже заполнены, кроме description — там сравнивается длина и заменяется только если новое значение длиннее.
- content_hash считается из title, grade, city, work_format, experience (без description). Изменение описания через enrich() не влияет на hash.
- Деактивация снятых вакансий происходит по отсутствию `id` в текущем прогоне.
- `grade` может быть диапазоном через дефис (`Middle-Senior`); левая часть считается минимальным грейдом для фильтрации.
- Доставка вакансий — per-user через таблицу `user_vacancy_delivery`; глобальный `notified_at` устарел.
- Таблица `user_vacancy_delivery` имеет колонку `status` с двумя значениями: `announced` и `delivered`. `announced` — вакансия попала в сводку или была в выдаче, когда пользователь нажал Хватит. `delivered` — карточка отправлена. При выдаче `get_undelivered_vacancies` исключает только `delivered` записи. `mark_announced` использует upsert с `ignore_duplicates`, чтобы не перезаписать `delivered`.
- Фильтрация находится в `delivery/filters.py`: пустой `filters` означает «показывать всё».
- `strict_mode` хранится в пользовательских фильтрах: `true` — вакансии с пустыми полями отсекаются, `false` — проходят.
- Функции ранжирования вакансий (classify_title, title_confidence, grade_score) находятся в delivery/ranking.py. Не дублировать в main.py или handlers.py.
- Callback prefixes: `ob:` — онбординг, `st:` — настройки, `st:blocked` — список заблокированных компаний в settings, `st:co:page:N` — пагинация списка компаний в settings, `st:pause` — постановка рассылки на паузу (доступно из /settings и из /stop prompt), `st:strict:toggle` — переключение strict_mode в настройках, `st:strict:toggle:exhaust` — переключение strict_mode из подсказки при exhausted, `more:` — пагинация выдачи, `hub:` — хаб returning user, `mute:` — подтверждение блокировки компании, `unmute:` — подтверждение разблокировки, `unmute_all:` — подтверждение массовой разблокировки. Текстовые сообщения `Вакансии` и `Настройки` обрабатываются как быстрые действия наравне с callback-командами.
- Webhook без `TELEGRAM_WEBHOOK_SECRET` не обрабатывает запросы (HTTP 500).
- Vercel proxy может передавать webhook с `Transfer-Encoding: chunked` без `Content-Length`; тело читается через `_read_request_body`, с декодированием HTTP chunks, а не как пустой JSON.
- Callback и message от `chat_id`, отсутствующего в таблице `users`, игнорируются (кроме `/start`).
- Аналитика событий: запись действий пользователя выполняется асинхронно, по принципу fire-and-forget. Ошибка записи события не должна влиять на работу бота или замедлять ответ пользователю.
- Аналитические события записываются через `db.log_event(chat_id, event, properties)`. Вызов размещается после основного действия и ответа пользователю. `log_event` не выбрасывает исключений.
- Callback prefix для аналитики отсутствует — события записываются внутри существующих обработчиков.
- Ссылки на вакансии в карточках оборачиваются в redirect через `build_redirect_url()`. Если redirect построить нельзя (нет `VERCEL_URL` или произошла ошибка), используется прямая ссылка на вакансию. Карточка должна отправляться в любом случае.
- Словарь вакансии, который возвращает `parse()`, не должен содержать служебных полей (с префиксом `_` или любых других, отсутствующих в таблице `vacancies`). Если парсеру нужно передать данные между `parse()` и `enrich()` — использовать атрибут экземпляра (`self._some_mapping`), не словарь вакансии.
- Если API требует динамический ключ (токен, API key), извлекаемый из HTML публичной страницы, парсер получает его при каждом запуске через GET + regex. Не хардкодить ключи.
- Браузерный этап (parsers/browser.py) запускается один раз перед всеми парсерами. Используется для получения динамических данных (buildId, cookies, токены) с сайтов, защищённых антиботом. Playwright разрешён ТОЛЬКО для page.goto(), page.content(), page.context.cookies(). Запрещены click(), fill(), locator() и любые взаимодействия с элементами страницы.
- Парсеры, которым нужны данные браузерного этапа, получают их через аргумент browser_secrets в parse(). Не запускать Playwright внутри парсера.
- curl_cffi используется как HTTP-клиент для сайтов, где WAF блокирует по TLS fingerprint. Параметр impersonate имитирует TLS handshake Chrome. Не использовать curl_cffi там, где достаточно aiohttp.
- User-Agent строится динамически из переменной окружения `CHROME_VERSION`. Не хардкодить версию Chrome в парсерах или `browser.py` — использовать `config.REQUEST_HEADERS`.
- При добавлении нового парсера — определить тип защиты по docs/antibot_playbook.md и выбрать транспорт. Задокументировать решение в реестре компаний playbook-а.

- Запрещено передавать ReplyKeyboardMarkup в `edit_message` / Telegram `editMessageText`; если нужно показать reply-клавиатуру, делай отдельный `send_message` после `edit_message` или `delete_message`.
- Runtime-запросы к `vacancies` не должны использовать `SELECT *`; указывать явный список колонок и не тянуть `source_json`, если raw payload не нужен по задаче явно.
- Битая вакансия в main pipeline пропускается полностью и не сохраняется частично; такие пропуски агрегируются в `skipped_count`.
- `hub:reset` не очищает `user_vacancy_delivery`; повторное открытие ранее просмотренных вакансий допускается только по явному выбору пользователя в соответствующей сводке.
- Блок сохранения и рассылки должен пытаться отправить admin report в `finally`, даже если прогон завершился частично.
- Контрактный тест предрелизного аудита: значение `vacancy.company`, возвращаемое парсером, должно совпадать с `companies.name`.
- Любые секреты источников (Bearer/API token), которые нельзя безопасно извлечь динамически, не хардкодятся в коде; временно допускается env-переменная. Отсутствие или невалидность такого секрета не должно валить весь pipeline: парсер пропускает источник, а ошибка попадает в admin report.
- AI-заглушки и будущие LLM-вызовы не должны вызываться из `_prepare_vacancy()`, normalizer или других обязательных runtime-этапов релизного пайплайна. AI-фаза подключается только отдельным явным шагом.
- Конфликт по vacancy `id` при вставке новой вакансии считается штатной ситуацией гонки и должен обрабатываться через `upsert`, а не через падение `insert`.

- Ручной сбор для @ProdRadar_bot запускается через scripts/collect_test.py: до pipeline проверяются отдельный Supabase URL, identity бота и отсутствие чужих пользователей. Исходная БД запрещена; тестовый workflow не имеет cron.
- Read-only DevTools-диагностика scripts/inspect_source_browser.py сохраняет только метаданные запросов и имена cookies/headers, без значений секретов; runtime browser stage остаётся общим в parsers/browser.py.
- Для явно разрешённого пользователем исследования фирменных API диагностический скрипт с явным --probe-tbank-pagination может нажать только «Показать ещё» в каталоге Т-Банка и сохранить публичные filters/pagination; формы отклика и отправка данных не используются. Runtime-ограничения browser.py сохраняются.
- Дополнительная официальная CA-цепочка применяется через parsers/tls.py только к проверенным source hosts; hostname/CERT_REQUIRED не отключаются. Временный NSS root для диагностического Chromium допустим только в одноразовом Actions runner и удаляется после запуска.

## Антипаттерны

Перед внесением изменений прочитай `docs/bugs.md` — там полный лог исправленных багов. Не повторяй их.
- Не извлекать структурированные поля (`grade`, `work_format`, `experience`) regex-ом из свободного текста (`meta description`, описания вакансий). Неструктурированные данные — задача AI-фазы.

## Текущие ограничения и известные проблемы

- В `supabase-py` нет метода `.not_in()`: использовать `.not_.in_("column", list)`.
- `maybe_single()` на некоторых версиях Supabase может давать `406`; безопаснее делать обычный `select()` и проверять пустой список.
- Любые утверждения AI-аудитора о коде проверяй по raw GitHub URL: аудитор может видеть кэшированную или устаревшую версию файла.

- Браузерный runtime служит только получению доступа через антибот/cookies/токены; вакансии собираются HTTP-запросами к API. HTML-описания обычным HTTP допустимы, если API не отдаёт полный текст; браузер не выгружает вакансии.

- Команды восстановления запускать через `scripts/run_profile.py --profile test`; явные TEST_* отображаются в стандартные имена только до импорта config, без fallback. Для будущего prod требуются отдельные PROD_* и проверка identity. Исходный token не использовать в test. Read-only аудит с --catalog-env не получает реквизиты БД/Telegram и использует справочники, прочитанные из тестовой БД.

- Настройка GitHub prodradar-test автоматизирована командой `scripts/run_profile.py --profile test configure-github`; bootstrap PAT читается только из GitHub environment secret отдельного setup job. Пакет содержит только test URL, ADMIN_CHAT_ID и sealed-box SUPABASE_KEY/TELEGRAM_BOT_TOKEN; реальные значения получать через Supabase Management и test Vercel, а не шифровать proxy placeholders. Repo Secrets и production не изменять. Настройка завершается read-only check, без collector.

- `requirements.txt` — только зависимости Vercel webhook/redirect. Сборщик/парсеры/тесты источников устанавливаются из `requirements-collector.txt`; Playwright/curl_cffi/bs4 не добавлять в webhook requirements. `.vercelignore` исключает сборщик из функций. Git previews ветки восстановления отключены для предотвращения роста Function Storage.
- Очистка Vercel через scripts/vercel_storage.py по умолчанию dry-run: полная пагинация и защита всех aliases/current/healthy rollbacks обязательны; historical original production не удаляются. Перед apply каждого кандидата повторно сверять защиту. Cron очистки не включать без отдельного поручения.

- Новый test VACANCY_PROFILE=project_bizdev разрешён пользователем. Product profile сохраняет прежние native groups и title rules. Общие каталоги включать только CAPTURE_ALL_ROLES; source_pool/role schema создаётся исключительно в test БД. Пул заменяется атомарно отдельно на успешный source; failed/устаревший/неполный snapshot не разрешает cached delivery и не снимает предыдущие вакансии.
- selection_profile/role_families/selection_version — реальные колонки новой test vacancies. Их нельзя запрашивать в исходной product БД; новые runtime projections должны быть условными. Не добавлять сервисные поля поверх vacancy вне колонок; причины классификации сохранять в source_json/отдельных аналитических данных.
- Project/bizdev правила находятся в delivery/roles.py; title-only отбор без отраслевых/skill фильтров. Ранжировать project выше bizdev, монетизацию не использовать как boost. Pool-only pipeline завершается до фильтрации/записи core vacancies и Telegram; обязательна интеграционная регрессия этого ограничения.
- Simple test flow — bot/simple_flow.py, prefix sm: (more:project/bizdev, settings, grade:N, grades:all, blocked, unmute:slug, pause). Legacy mute/unmute подтверждения сохраняются; старые onboarding/hub/more callbacks ведут в простой поиск. Product webhook продолжает старый dispatcher. Не смешивать bizdev в первую project страницу.
- Большие source pools публиковать через stage batches + commit_source_pool с проверкой expected count. Ограничение RADAR_POOL_SOURCES разрешено только SOURCE_POOL_ONLY; workflow inspect_sources при capture_pool_only означает имена источников для адресного восстановления.
