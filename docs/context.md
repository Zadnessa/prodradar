# Контекст проекта ProductRadar

## Продуктовые решения

- `grade` берётся из API, через маппинг `experience -> grade`, либо из заголовка только для исключений Avito и T-Bank (`Lead+`). Универсальный `grade_guesser` удалён.
- Enrichment реализуется методом `enrich()` внутри конкретного парсера, а не отдельным слоем файлов.
- Для T-Bank, VK и Avito полное описание вакансии извлекается из SSR HTML-страницы, а не из API. У Avito дополнительно используется JSON-LD `JobPosting`, откуда берётся и `datePosted`.
- Шаг `Компании` убран из онбординга: сценарий `/start` → welcome → `grade` → `city` → `work_format` → `confirm` → мгновенный quick-path без дополнительных шагов и без strict_mode disclaimer → выдача вакансий. Первая сводка честно маркирует режим без фильтров и направляет в `/settings` для настройки под себя. Управление компаниями доступно через `/settings` (пагинация по 8 компаний на страницу) и `/mute_{slug}` из карточек вакансий.
- Колонка `slug` в таблице `companies` — уникальный строковый идентификатор компании для user-facing слоя (`callback_data`, команды `mute/unmute`, карточка вакансии). `parser_name` — идентификатор парсера, может повторяться для компаний с паттерном «один парсер — несколько компаний».
- В настройках компаний сортировка фиксируется при входе в список: сначала заблокированные (`excluded_companies`) по алфавиту, затем остальные по алфавиту; при toggle внутри сессии порядок не пересчитывается.
- Сортировка списка компаний выполняется по колонке `sort_name` (русская транслитерация) из таблицы `companies`. `sort_name` используется только для сортировки, в кнопках отображается `name`.
- Toggle компании в `/settings` работает через immediate write: каждое нажатие кнопки сразу обновляет `excluded_companies` в БД. Кнопка «Сохранить» для компаний просто возвращает в меню.
- `strict_mode` управляется toggle-кнопкой в меню настроек (`st:strict:toggle`). При `vacancy_exhausted` показывается контекстная подсказка с предложением переключить режим.
- Обновлена редактура user-facing copy: welcome, шаги онбординга, on-demand summaries, zero-state и exhausted-сценарии. Disclaimer перед `ob:strict:off/on` теперь динамический (`XX/YY/ZZ`) и считается в `handlers` по текущим фильтрам пользователя.
- В exhausted-сценариях базовый CTA переведён на inline-кнопку `⚙️ Фильтры` (`st:menu`) без reply-клавиатуры; при `strict_mode=true` дополнительно сохраняется quick-toggle `st:strict:toggle:exhaust` отдельной строкой.
- В меню настроек пояснение про неполные вакансии зависит от `strict_mode`: при выключенном режиме неполные вакансии показываются, при включённом скрываются.
- Loader-сообщения в bot-сценариях используют Telegram custom emoji `5451732530048802485` вместо обычного `⏳`.
- Таблица `user_vacancy_delivery` хранит два статуса: `announced` (вакансия показана в сводке, карточка не отправлена) и `delivered` (карточка отправлена). `announced_at` и `delivered_at` фиксируют время каждого перехода. Дельта `delivered_at - announced_at` используется как метрика time-to-open.
- Кнопка «Хватит» при пагинации помечает все оставшиеся вакансии как `announced`, чтобы scheduled-рассылка не показывала их как новые.
- После завершения онбординга и после save в `/settings` при изменённых фильтрах бот разделяет найденные вакансии на новые и ранее просмотренные и показывает выбор: `Показать все` или `Только новые`.
- `hub:reset` (сценарий «Начать заново») сбрасывает только фильтры и перезапускает онбординг; история `user_vacancy_delivery` не очищается.

- Scheduled-рассылка различает реально новые вакансии (нет записи в `user_vacancy_delivery`) и ранее анонсированные (`status=announced`). Текст вводного сообщения отражает это разделение.
- Scheduled-сценарий `new=0, announced>0` должен быть action-oriented: сообщение не тупиковое, а с выбором `Посмотреть (M)` / `Не сейчас`.
- Для scheduled-рассылки формулировка «по твоим фильтрам» допустима только если у пользователя реально заданы базовые фильтры (`grades`, `cities`, `work_formats`); при пустых фильтрах используется нейтральный intro `N новых вакансий.`

- При малом количестве вакансий после фильтрации (до 5) бот показывает текст scarcity: объясняет, что фильтры узкие, мониторинг продолжается.
- Если on-demand выдача пуста из-за отсутствия undelivered, но по текущим фильтрам есть ранее просмотренные вакансии — показывается кнопка `Показать просмотренные (N)` с callback `more:reseen:0`.
- On-demand витрина: первые 10 вакансий формируются по одному лучшему представителю от каждой компании, отсортированных по `title_boost (только on-demand) → title_confidence → grade_score → published_at DESC`. Последующие пачки — плоский список по тому же ключу. `TITLE_BOOST_GROUPS` определены в `config.py`.
- Для returning user команда `/start` показывает хаб с тремя вариантами: получить вакансии, открыть настройки, начать заново. `/start` снимает паузу рассылки.
- Постоянная ReplyKeyboard с двумя кнопками (`Вакансии`, `Настройки`) показывается после онбординга и остаётся до `/stop`; `/stats` временно отключён на период релиза.
- В фильтрах пустой список означает «всё». `strict_mode=true` отсекает вакансии с пустыми полями, `strict_mode=false` пропускает их.
- В онбординге используются два города — Москва и Санкт-Петербург — плюс вариант «Любой город». Это осознанное решение после анализа данных.
- Текст отписки должен быть честным: при `/stop` фильтры сохраняются.
- Кастомные эмодзи брендов берутся из таблицы `companies`: колонка `custom_emoji_id` хранит Telegram custom emoji id. При формировании сообщений используется HTML-тег `tg-emoji` с fallback на обычный `emoji`. Фича требует Telegram Premium у владельца бота.
- Блок `опубликовано` показывается только если у вакансии есть реальный `published_at` из источника. Fallback на `created_at` удалён, чтобы не вводить пользователя в заблуждение.
- Сортировка выдачи вакансий: сначала `published_at` по убыванию (реальная дата, `NULL` в конце), затем `created_at` по убыванию.
- `title_confidence` — числовой score (`exact=3`, `regex=2`, `grey=1`) для обеих выдач. `grade_score` — матричная функция близости грейда вакансии к пользовательским грейдам (0-4): при пустом списке пользовательских грейдов или пустом/нераспознанном grade вакансии возвращает 0. Единая сортировка: `title_boost` (только on-demand) → `title_confidence` → `grade_score` → `published_at DESC`.
- `salary` не хранится в БД и не извлекается парсерами. Рыночная аналитика зарплат — задача AI-фазы или партнёрства.
- `content_hash` вычисляется из `title + grade + city + work_format + experience` через разделитель `|` и используется для определения изменений вакансии.
- Если `content_hash` совпадает с сохранённым значением, обновляется только `last_seen_at`; если хеш изменился, выполняется полный upsert записи.
- Для новых вакансий конфликт по `id` считается штатной ситуацией гонки и обрабатывается через `upsert(on_conflict="id")`, а не через падение `insert`.
- Битые вакансии пропускаются полностью (без частичной записи в БД), агрегируются в `skipped_count` и отражаются в admin report.
- Блок сохранения/рассылки обязан пытаться отправить admin report в `finally`, даже если прогон завершился частично.

- Вакансии, которые отсутствуют в текущей выдаче API, деактивируются через `is_active=false`.
- `description` хранит полный текст описания без ограничения длины, чтобы AI-фаза работала с полными данными.
- `source_json` остаётся в таблице `vacancies` для отладки и AI-фазы, но не участвует в runtime-запросах пользовательской выдачи (явный список колонок вместо `SELECT *`).
- AI-хуки и заглушки (включая `generate_summary()`) не должны вызываться внутри `_prepare_vacancy`, normalizer и других обязательных runtime-этапов до Wave 7.

- Если `experience = 'не указан'` и `grade` заполнен, `experience` выводится из `grade` через обратный маппинг.
- Матч диапазона грейда остаётся широким: вакансия вида `Middle-Senior` проходит по любой части диапазона; точное совпадение решается ранжированием, а не фильтрацией.
- Если `city = 'Не указан'` и `work_format` содержит `Удалёнка`, `city` автоматически заменяется на `Удалёнка`.
- Для T-Bank `city_slug` в URL вакансии всегда фиксирован как `moscow`: это даёт SSR HTML-секции для вакансий из любого города, а фактический город по-прежнему берётся из `regionId` через `city_mappings`.
- Настройки двухуровневые: базовые (`grade`, `city`, `work_format`) и расширенные (компании по отраслям). В расширенных используется blacklist-логика: всё включено по умолчанию.
- Каждая карточка вакансии содержит кликабельную команду `/mute_{slug}` для блокировки компании. При нажатии бот запрашивает подтверждение через inline-кнопку. Компания добавляется в `filters.excluded_companies` по `name` (русское название). Команда `/blocked` показывает список заблокированных с командами `/unmute_{slug}` и кнопкой «Управлять компаниями» (ведёт в settings). Команда `/unmute_all` разблокирует все компании. Первое использование mute показывает подсказку про `/settings` (флаг `has_used_mute` в `filters`), последующие — нет. Inline-кнопка «Заблокировать другие компании» присутствует в ответе на каждый успешный mute и ведёт на `st:edit:company`.
- После `unmute` и `unmute_all` бот предлагает inline-кнопку «Получить вакансии» (`st:deliver`) для немедленного просмотра разблокированных позиций. Для одной компании текст кнопки содержит название компании.
- Сценарии mute / unmute / unmute_all уплотняются до одного итогового сообщения с inline CTA без второго дублирующего сообщения.
- В `/settings` отдельная кнопка `Заблокированные (N)` показывается только если `N > 0`.
- Подбадривающее сообщение после первой пачки показывается только для первого on-demand запроса пользователя.

- Отрасли (`category`) определяются на уровне компании как временное решение. Внутри экосистем (Сбер, Яндекс, МТС) разные команды могут относиться к разным отраслям — разрешение на уровне вакансий делается в AI-фазе.
- AI-результаты хранятся в отдельной таблице `vacancy_ai_enrichment` с kill switch. Таблица `vacancies` не модифицируется AI-шагом.
- Продуктовое позиционирование: «курация компаний с продуктовой культурой», а не агрегация вакансий. 20+ компаний — обязательное условие релиза. Целевые сегменты пользователей: активные соискатели (объём и свежесть) и пассивные наблюдатели рынка (низкий шум, точные фильтры).
- API-ресерч новых компаний делегируется ChatGPT батчами по 3 компании и проходит в два шага: extraction (все эндпоинты, поля, пагинация) и audit (фильтрация релевантного для бота). Результаты верифицируются вручную и фиксируются в docs/api_spec.md.
- Аналитика пользовательских действий хранится в таблице `user_events` (id, chat_id, event, properties jsonb, created_at). Запись идёт через `SupabaseService.log_event(chat_id, event, properties)` в режиме fire-and-forget: ошибка записи не влияет на UX.
- Redirect-эндпоинт `api/go.py` отслеживает клики по карточкам вакансий: принимает GET с параметрами `vacancy_id`, `chat_id`, `source`, `company`, `grade`, `title_confidence`, `city`, `work_format`, `url`; пишет событие `vacancy_clicked` в `user_events`; затем всегда возвращает HTTP 302 на оригинальный URL. Если запись события не удалась — редирект всё равно выполняется. Если `REDIRECT_BASE_URL` отсутствует, карточка использует прямую ссылку как fallback. Переменная содержит production-домен Vercel (например, prodradar.vercel.app). Системная `VERCEL_URL` не используется, т.к. указывает на preview-деплоймент с авторизацией.
- В таблице `users` используются дополнительные поля Telegram User: `language_code` (text), `is_premium` (boolean), `first_name` (text), `last_name` (text). Поля обновляются при каждом `/start`.
- События аналитики и назначение: `onboarding_started` (старт онбординга), `onboarding_path_chosen` (выбор quick/step-by-step), `onboarding_step_completed` (завершён шаг онбординга), `onboarding_completed` (онбординг завершён), `onboarding_restarted` (перезапуск онбординга), `vacancy_summary_shown` (показана сводка выдачи), `vacancy_empty_result` (пустой результат), `vacancy_page_viewed` (показана страница вакансий), `vacancy_stopped` (пользователь остановил выдачу), `vacancy_exhausted` (достигнут конец выдачи), `scheduled_delivery_sent` (плановая рассылка отправлена), `scheduled_delivery_empty` (в рассылке нечего показывать), `settings_opened` (открыты настройки), `filter_saved` (сохранён фильтр), `company_toggled_in_settings` (в настройках переключена компания), `company_muted` (компания заблокирована), `company_unmuted` (компания разблокирована), `all_companies_unmuted` (массовая разблокировка), `bot_stopped` (остановка бота), `user_returned` (returning user в хабе), `mailing_paused` (пауза рассылки), `mailing_resumed` (возобновление рассылки), `stats_viewed` (просмотр статистики), `vacancy_clicked` (пользователь открыл вакансию по ссылке; properties: `vacancy_id`, `source`, `company`, `grade`, `title_confidence`, `city`, `work_format`, `os`).
- Фильтрация заголовков четырёхшаговая и унифицированная: сначала абсолютный pre-filter `TITLE_PREFILTER_REJECT` (безусловное отсечение до любых зон), затем `TITLE_EXACT_WHITELIST` (безусловный пропуск), затем `TITLE_REGEX_PATTERNS` + `TITLE_BLACKLIST_PATTERNS`, и затем `TITLE_GREY_PATTERNS` + `TITLE_BLACKLIST_PATTERNS`. Серая зона остаётся временным решением до AI-фазы (Wave 7).
- Exact-подстроки в `TITLE_EXACT_WHITELIST` используют точные падежные формы (менеджер продукта, менеджер по продукту, владелец продукта и т.д.), а не усечённые основы. Вакансии с нестандартными формулировками (менеджер по продуктовому маркетингу) проваливаются в regex-зону, где blacklist их отсекает. Принцип: exact = безусловный пропуск, поэтому точность подстрок критична.
- Per-company whitelist (SBER/DOMCLICK/HH/KASPERSKY) удалены. Поле `is_product_role` и служебное `_source` удалены из HH-парсеров и больше не участвуют в пайплайне фильтрации.
- Grade override из заголовка применяется после `normalize_grade()` и `grade_from_experience()`: `младш*`/`junior` → `Junior`, `head of product`/`chief product`/`cpo`/`директор.*продукт` → `Lead+`.
- HH.ru планируется использовать в двух ролях: как источник вакансий (парсер по employer_id) и как валидатор полноты фирменных джоббордов. Дедупликация между HH и фирменным сайтом откладывается до AI-фазы (embeddings + cosine similarity), потому что синтаксические различия в описаниях делают строковое сравнение ненадёжным.
- Фирменный парсер Циан (parsers/cian.py) отключён (is_enabled=false) из-за WAF-блокировки на GitHub Actions. Вакансии Циана добавляются через HH API (parser_name=hh_cian). Файл cian.py и регистрация в PARSER_REGISTRY сохранены для возможного включения после переезда на VPS.
- HH-парсеры для компаний без доступного карьерного сайта: отдельный файл parsers/hh_[slug].py, отдельная строка в companies с parser_name=hh_[slug], name совпадает с фирменным названием компании. Vacancy ID формируется как hh_[slug]_{hh_id}. При появлении единого HH-сканера (Wave 8) индивидуальные HH-парсеры выключаются.
- Закрытые вакансии не удаляются из таблицы vacancies (is_active=false). Данные о времени жизни вакансий (created_at, last_seen_at, будущий deactivated_at) используются для рыночной аналитики.
- Админ-отчёт содержит per-parser статистику: количество собранных вакансий по каждому парсеру и классифицированные ошибки с тегами [BLOCKED], [TIMEOUT], [NOT_JSON], [HTTP_xxx], [ERROR]. Детальное логирование внутренних операций парсеров (пагинация, enrichment-счётчики) отложено до Wave 6.

- ВТБ исключён из списка компаний. Причина: нахуй ВТБ.
- Классификация сложности источников при добавлении новых компаний: Тип A — чистый JSON API для списка и detail, стандартная пагинация, без антибота (~20 минут на парсер). Тип B — JSON API для списка, description только через HTML-страницу (~40-60 минут, средняя хрупкость). Тип C — нет JSON API, всё через HTML SSR (1-2 часа, высокая хрупкость). Тип D — SPA, антибот, JS-challenge, динамические токены (полдня+, максимальная хрупкость, требует Playwright). Тип определяется до начала работы над парсером.
- Playwright используется как второй транспорт только для компаний типа D (антибот, JS-рендеринг). Компании типа A и B работают через aiohttp. Решение не переводить все парсеры на Playwright.
- Playwright используется как генератор сессии (cookies, buildId, токены), не как навигатор. Один запуск Chromium перед всеми парсерами, результаты передаются в словаре browser_secrets. Stealth-настройки: отключение navigator.webdriver, реалистичный UA, viewport 1920x1080, locale ru-RU. Список сайтов для браузерного этапа хардкодится в parsers/browser.py.
- Chrome User-Agent собирается в `config.py` из переменной окружения `CHROME_VERSION` (с дефолтом на актуальную версию). Все HTTP-клиенты (`aiohttp`, `curl_cffi`, Playwright) используют единый UA из `config.REQUEST_HEADERS`.
- curl_cffi используется как третий транспорт (после aiohttp и Playwright) для сайтов, где WAF блокирует по TLS fingerprint (waf-verdict: challenge). impersonate="chrome131" имитирует TLS handshake Chrome, что позволяет обходить challenge без cookies и без Playwright.
- Классификация транспортов: (1) aiohttp — основной, для чистых API без антибота. (2) Playwright — генератор сессии (cookies, buildId, токены), один запуск перед всеми парсерами. (3) curl_cffi — HTTP-клиент с TLS impersonate, для сайтов с WAF challenge по fingerprint. Выбор транспорта определяется при исследовании API новой компании.
- При добавлении нового парсера обязателен INSERT в таблицу companies в Supabase. Поля: name, parser_name, emoji, is_enabled=true. custom_emoji_id и category — NULL до заполнения.
- Паттерн «динамический API-ключ»: если API требует ключ, который вшит в HTML публичной страницы и может обновляться, парсер при каждом запуске делает GET на публичную страницу, извлекает ключ regex-ом и использует для запросов. Ключ не хардкодится. Пример: МТС (x-api-key из window.__NUXT__).
- MTS Link временно использует Bearer-токен из env-переменной `MTSLINK_BEARER_TOKEN`; отсутствие или невалидность токена не валит общий прогон: источник пропускается, причина уходит в admin report.
- `parsers/mts.py` обязан соблюдать общий контракт `enrich()`: `description` обновляется только если новое значение длиннее текущего.

- Паттерн «один парсер — несколько компаний»: если на одном карьерном сайте размещены вакансии нескольких самостоятельных брендов, парсер проставляет разные значения company на основе данных API (подразделение, юрлицо, бренд). Каждый бренд регистрируется как отдельная запись в таблице companies со своим emoji и category. Пример: МТС (МТС, МТС Банк, MWS.AI, KION, Юрент через BRAND_MAP).


### Отклонённые UX-решения

- Группировка компаний по категориям (drill-down) — отклонена. Пользователь хочет видеть список компаний, а не категорий.
- Мини-аппы Telegram — отклонены. Дропы онбординга, отдельный хостинг, часть юзеров не откроет.
- Свободный текстовый ввод для фильтров — отклонён. Ломает архитектуру бота.
- Умные пресеты на основе поведения — отложены до сбора данных.
- Дайджест vs карточки — отложен до сбора фидбека после релиза.
- Кнопки на карточках (сохранить, скрыть, похожие) — отложены до сбора фидбека после релиза.

## Experience-to-grade маппинг

| Нормализованный опыт | Грейд |
| --- | --- |
| без опыта | Junior |
| до 1 года | Junior |
| 1-3 года | Middle |
| 3-5 лет | Middle+ |
| 5+ лет | Senior |
| lead/head/руководитель/директор/cpo в заголовке | Lead+ |
| не указан | null |

Дополнительно используется regex-fallback: если в строке опыта найдено число `N`, то `N < 1 → Junior`, `1 ≤ N < 3 → Middle`, `3 ≤ N < 5 → Middle+`, `N ≥ 5 → Senior`.
