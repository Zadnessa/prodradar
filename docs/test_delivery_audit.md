# Проверка тестовой доставки

Workflow `.github/workflows/audit_test_delivery.yml` читает только TEST Supabase
`jmsdxgylyjxwdwmdrmxw`. Он запускается при изменении своего файла в ветке
`codex/audit-test-delivery` либо вручную, использует environment
`prodradar-test` и не отправляет Telegram-сообщений.

Проверка сопоставляет `users.filters`, `vacancies.role_families` и
`user_vacancy_delivery.status`. У каждого пользователя отдельно считает
отправленные карточки за сохранённую историю, подходящие активные вакансии
и неприсланный остаток. Project, bizdev и смешанные роли разделены;
смешанная вакансия считается один раз. Старые role-предпочтения показаны
отдельно от фильтров, которые фактически использует короткий test-флоу.

В отчёт попадают только обезличенные агрегаты и настройки отбора.
Chat ID, имена, контакты, тексты вакансий и ключи не выводятся.
Запросы к БД выполняются только методом GET. Админ определяется по
`ADMIN_CHAT_ID`; коллега обозначается отдельно, если кроме админа
есть ровно один активный пользователь с завершённым онбордингом.

Runtime-фильтр берётся из проверенного коммита test-ветки
`2110223fa572c4ef722850142be0a15fd74be846`. После изменения логики отбора
этот ref нужно обновить. Concurrency совпадает со сборщиком, чтобы диагностика
не выполнялась посреди его записей. Интерактивные действия пользователей
могут менять историю во время проверки; время снимка указано в отчёте.

Изменение пользовательских настроек выполняется отдельно после проверки
причины. История доставки не сбрасывается ради повторной выдачи.
